# 🐛 ProNeighbor Bug Report

Based on my analysis of the ProNeighbor codebase using MCP, I've identified several categories of bugs and potential issues. Here's a comprehensive report:

## 🔴 Critical Bugs

### 1. Type Safety: Unsafe Type Assertion in `AuthContext.tsx`
**File:** `src/contexts/AuthContext.tsx`  
**Location:** `toFirestoreTimestamp` function (line ~100)

```typescript
function toFirestoreTimestamp(value: unknown): FirestoreTimestamp {
  return (value ?? null) as FirestoreTimestamp; // ❌ Unsafe assertion
}
```

**Issue:** This blindly casts any value to `FirestoreTimestamp` without validation. If Firestore returns a plain object or string instead of a Firebase Timestamp, this will cause runtime errors when `.toDate()` or `.toMillis()` is called.

**Fix:**
```typescript
function toFirestoreTimestamp(value: unknown): FirestoreTimestamp | null {
  if (value instanceof Timestamp) return value;
  if (value && typeof value === 'object' && 'seconds' in value) {
    return Timestamp.fromMillis((value as any).seconds * 1000);
  }
  return null; // or throw with context
}
```

### 2. Security: Email Verification Logic Flaw in `ProtectedRoute.tsx`
**File:** `src/components/auth/ProtectedRoute.tsx`  
**Location:** `requireVerified` check (line ~55)

```typescript
const isEmailApprovedByAdmin = userProfile?.emailVerified === true;
if (isPasswordProvider && !user.emailVerified && !isEmailApprovedByAdmin) {
  return <Navigate to="/dashboard?verifyEmail=1" replace />;
}
```

**Issue:** The `userProfile.emailVerified` field is manually managed and may not be synchronized with Firebase Auth's `user.emailVerified`. An admin could set this to `true` without the user actually verifying their email, bypassing security.

**Fix:** Remove the `userProfile.emailVerified` check and rely solely on `user.emailVerified` from Firebase Auth, or implement a proper sync mechanism with audit logging.

### 3. Race Condition: Profile Creation in `AuthContext.tsx`
**File:** `src/contexts/AuthContext.tsx`  
**Location:** `createUserProfile` function

```typescript
const snap = await getDoc(ref);
if (!snap.exists()) {
  // Create profile...
}
```

**Issue:** In high-concurrency scenarios (e.g., rapid signups), two requests could both pass the `!snap.exists()` check and attempt to create the profile, causing a write conflict or duplicate referral code generation.

**Fix:** Use a Firestore transaction or a unique constraint on the referral code field:
```typescript
await runTransaction(db, async (tx) => {
  const snap = await tx.get(ref);
  if (!snap.exists()) {
    tx.set(ref, profile);
    // Also set referral code doc atomically
  }
});
```

### 4. Error Handling: Information Leakage in `deleteAccount`
**File:** `src/contexts/AuthContext.tsx`  
**Location:** `deleteAccount` catch block

```typescript
} catch (e: unknown) {
  const code = (e as { code?: string }).code;
  if (code === "auth/wrong-password") return { success: false, reason: "Incorrect password." };
  // ... other generic messages
  return { success: false, reason: "Deletion failed. Try again." };

```

**Issue:** While the messages are generic, returning structured error reasons could be exploited for enumeration attacks. Also, the type assertion `(e as { code?: string }).code` is unsafe.

**Location:** `healProfessionalAggregates` called within `listProfessionals`

```typescript

      // ... recalculateProRating makes a Firestore query per profile
```

## 🟢 Medium/Low Priority Issues

### 7. Type Safety: Unsafe Validation Error Formatting
**File:** `src/lib/validation.ts`  
**Location:** `validateInput` function

```typescript
const messages = (error as z.ZodError<unknown>).issues
  .map((issue: z.ZodIssue) => `${String(issue.path).replace(/,/g, ".")}: ${issue.message}`)
  .join("; ");
```

**Issue:** `String(issue.path)` on an array produces `"field,subfield"` format, which is then replaced with dots. This is fragile and could misrepresent nested field paths.

**Fix:** Use Zod's built-in `format()` or `flatten()` methods for consistent error formatting.
