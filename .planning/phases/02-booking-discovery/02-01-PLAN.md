# Plan 02-01: Schema Fallback Booking Queries

## Objective

Ensure both client and pro booking lists load correctly for legacy and current schema fields, and sort newest-first consistently.

## Context

The codebase currently has mixed booking schema usage (`clientUid` vs `clientId`, `proUid` vs `proId`) and list sorting must remain newest-first. We need query logic that gracefully falls back to legacy field names without duplicates.

## Tasks

### Task 1: Inspect existing booking queries
- Locate current client booking and pro booking query functions in `src/services/firestoreService.ts`
- Identify current field names and sort order
- Confirm whether current UI depends on direct service return shape

### Task 2: Implement client booking fallback
- Update client booking loader to query `clientUid` first
- If no results, query `clientId`
- Merge/dedupe results if both paths exist
- Preserve newest-first ordering by `createdAt` descending

### Task 3: Implement pro booking fallback
- Update pro booking loader to query `proUid` first
- If no results, query `proId`
- Merge/dedupe results if both paths exist
- Preserve newest-first ordering by `createdAt` descending

### Task 4: Validate query order and output shape
- Ensure returned arrays remain compatible with callers
- Verify sorting is applied consistently
- Document any schema assumptions or edge cases

## Verification

- Build succeeds with zero TypeScript errors
- Query functions return merged unique records
- Newest-first order preserved for both booking paths
- No regressions in callers using existing booking service methods

## Success Criteria

- Client bookings load for both current and legacy client ID fields
- Pro bookings load for both current and legacy pro ID fields
- Lists are sorted newest-first
- No duplicate bookings in merged results
